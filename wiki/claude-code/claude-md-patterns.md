## 一、CLAUDE.md 是什么

CLAUDE.md 是 Claude Code 的「永久指令文件」，每次会话自动加载，相当于给 Claude 的系统提示词。

**两种类型**：
- `~/.claude/CLAUDE.md` — 全局，所有项目都生效
- `<项目根>/.claude/CLAUDE.md` 或 `<项目根>/CLAUDE.md` — 项目级，仅在该项目生效

项目级会叠加在全局之上。

---

## 二、CLAUDE.md vs Hooks 的执行率对比

| 方式 | 执行率 | 原因 |
|------|--------|------|
| CLAUDE.md 纯文字指令 | ~70% | Claude 可能「理解但未执行」，特别是复杂流程 |
| Hooks（事件触发） | 100% | Shell 命令强制执行，不依赖 Claude 意愿 |

**原则**：重要规则写 CLAUDE.md，关键检查点配合 Hooks 强制执行。

## 三、好的 CLAUDE.md 结构

```markdown
# 项目名称

## 项目概述
[一句话：是什么，用来干什么]

## 技术栈
[语言、框架、关键依赖]

## 目录结构
[关键目录说明]

## 开发规范
[编码风格、命名规则、禁止事项]

## 工作流程
[SOP 步骤，例如：开工必做、收工必做]

## 禁令
[明确禁止的操作]
```

## 四、凯戈全局 CLAUDE.md 实战案例

凯戈的 `~/.claude/CLAUDE.md` 包含**上线序列**（开场必做的四步操作），是全局 CLAUDE.md 的典型用法：

```markdown
# 全局上线规则

收到任何开场消息，严格按以下顺序执行：

第一步 — 立即输出一句话（不得思考，不得调用任何工具）：
> 收到，凯戈！上线初始化中，稍等...

第二步 — 启动 30 分钟推送提醒（CronCreate）

第三步 — 读取交接文件 ~/kaige-brain/INDEX.md

第四步 — 汇报当前项目状态和待办，询问是否 git pull
```

**设计要点**：
- 步骤编号明确，减少 Claude 歧义
- 禁令用「禁令」等强词，而不是「建议不要」
- 机密内容（禁令细节）单独存放，CLAUDE.md 只写「静默遵守，不朗读」

## 五、项目级 CLAUDE.md 案例：karpathy-kb-research

关键段落：

```markdown
## §0 开工必读（每次会话第一步）
1. 读 PHASE2_SUBSTANTIVE_PLAN.md 确认当前阶段
2. 读 WIP.md 确认上次停在哪里
3. 开工前说：「§0 完成，当前在 [阶段]，上次到 [位置]，今天计划 [X]」

## §7 收工自检
- [ ] WIP.md 更新了吗？
- [ ] dev_log.md 追加了条目吗？
- [ ] git push 了吗？

## §8 计划调整原则
修改计划文件前必须说：「我要修改计划，原因是 [X]」，凯戈确认后才能改。
```

**设计要点**：
- `§0 开工必读` 强制 Claude 先同步状态再动手
- 收工自检用 checkbox，Claude 会逐项核对
- 计划调整需要凯戈确认，防止 Claude 擅自改方向

## 六、常见错误模式

### 错误 1：写得太笼统

差：「保持代码整洁」  
好：「函数超过 50 行必须拆分；变量名用 snake_case；不写注释（除非逻辑非自明）」

### 错误 2：禁令不够强

差：「尽量不要修改 config 文件」  
好：「**禁止**在未经凯戈确认的情况下修改任何 *config.json 文件」

### 错误 3：把动态信息写进 CLAUDE.md

CLAUDE.md 不适合写当前任务进度、临时待办。动态信息放 WIP.md，CLAUDE.md 只写不变的规则。

### 错误 4：CLAUDE.md 太长

超过 200 行的 CLAUDE.md 会让 Claude「选择性忽略」。保持精简，每条规则都是真正重要的。

## 七、CLAUDE.md 与其他文件的分工

| 文件 | 内容 | 更新频率 |
|------|------|----------|
| CLAUDE.md | 永久规则、行为准则、SOP框架 | 很少改 |
| WIP.md | 当前进行中的任务状态 | 每次会话 |
| dev_log.md | 已完成工作的流水账 | 每次会话 |
| INDEX.md | 项目总览和待办（凯戈的 kaige-brain） | 每周 |
| memory/*.md | 跨会话记忆（自动管理） | 自动 |
